## Context

ADR005 introduced the `external/notifier` package with two channel senders:
Web Push (active) and FCM (plumbed but disabled). A typical Flutter client
can expose a `NotificationTokenProvider` abstraction with a `Noop` default
until a real Firebase provider is wired.

Phase 1 proved the architecture works end-to-end for Web Push. Phase 2
activates FCM for Android and iOS. The primary changes span GHATD, a host application, and a mobile client:

- **ghatd** — framework: credential config, sender activation, token
  invalidation, `Config` endpoint expansion.
- **host application** — deployment: secret injection, env var plumbing,
  production values.
- **mobile client** — Firebase token provider, `firebase_messaging`
  integration, permission handling, token refresh, logout cleanup.

No Firebase packages, credentials, or platform files
(`GoogleService-Info.plist`, `google-services.json`) are included here. The
platform setup notes below are a rollout checklist only; the actual Firebase
project setup and generated files remain outside this ADR.

### Implementation update (2026-08-01)

GHATD now provides `NewStandardSenders`, which activates FCM only when it is
explicitly enabled, resolves file or base64 credentials, and returns a cleanup
function for temporary credential files. Environment-variable names remain a
host-application concern rather than part of the notifier package API.

FCM batch responses now retain per-token failure detail in the returned error,
but automatic invalid-address cleanup is still incomplete: `FCMSender` does not
invoke its installed invalid-address handler. The sender continues to use
multicast delivery when more than one token is present.

## Decision

### 1. Firebase credential shape (server-side)

The `FCMSenderConfig` struct already defines the credential surface:

```go
type FCMSenderConfig struct {
    Enabled         bool
    CredentialsFile string   // path to Firebase service-account JSON
    ProjectID       string   // GCP project ID (alternative to file)
}
```

**No change to this struct.** The two-path design (file OR project ID) covers
both local dev (file-based) and cloud deployments (ADC/metadata). The host
application environment mappings shown here (`NOTIFIER_FCM_CREDENTIALS_FILE`,
`NOTIFIER_FCM_PROJECT_ID`) are sufficient for that deployment; GHATD itself
does not prescribe those variable names.

### 2. Firebase credential shape (mobile client)

The Flutter app needs a Firebase project configuration. This is provided by
platform-specific files that are **outside the scope of this plan**:

- Android: `google-services.json` (placed in `android/app/`)
- iOS: `GoogleService-Info.plist` (placed in `ios/Runner/`)

These files are generated by the Firebase Console and contain the `sender_id`,
`project_id`, `api_key`, `client_id`, `app_id`, and `database_url`. They must
be added to the repository's `.gitignore` or injected during CI.

### 3. Mobile token provider implementation

Add a `firebase_messaging` dependency to `pubspec.yaml` and create
`FcmNotificationTokenProvider` implementing the existing `NotificationTokenProvider`
interface:

```dart
final class FcmNotificationTokenProvider implements NotificationTokenProvider {
  @override
  bool get isAvailable => true;

  @override
  Future<String?> getToken() async {
    final messaging = FirebaseMessaging.instance;
    await messaging.requestPermission();
    return messaging.getToken();
  }
}
```

Key behaviours:

- `isAvailable` is a synchronous `true` — the store uses this to show/hide
  the "Register" button. If Firebase is not initialised at startup (missing
  platform config), `getToken()` will throw; the store's try/catch handles
  this gracefully.
- `requestPermission()` is called inside `getToken()` rather than at app
  startup so the system prompt only appears when the user explicitly taps
  "Register" in settings.
- Token refreshes are handled via `FirebaseMessaging.instance.onTokenRefresh`
  — the provider exposes a `Stream<String>` that the store subscribes to
  for re-registration.

### 4. Token refresh and re-registration

`FcmNotificationTokenProvider` exposes a `tokenChanges` stream:

```dart
abstract interface class NotificationTokenProvider {
  bool get isAvailable;
  Future<String?> getToken();
  Stream<String> get tokenChanges;  // new
}
```

The store listens to `tokenChanges`. When a new token arrives:

1. Check the user is still authenticated.
2. Call `registerFcmAddress()` with the new token.
3. The server upserts on `channel + address_hash`, so the old address record
   is updated in-place — no stale token cleanup needed on the client.

The `NoopNotificationTokenProvider` returns `const Stream.empty()`.

### 5. Server sender activation

In the host application server wiring, the FCM sender should be wired like this:

```go
if settings.NotifierFCMEnabled {
    credsFile, err := notifier.ResolveCredentialsFile(
        settings.NotifierFCMCredentialsFileB64,
        settings.NotifierFCMCredentialsFile,
    )
    if err != nil {
        return fmt.Errorf("resolve FCM credentials: %v", err)
    }
    notifierService.WithSender(notifier.NewFCMSender(notifier.FCMSenderConfig{
        Enabled:         settings.NotifierFCMEnabled,
        CredentialsFile: credsFile,
        ProjectID:       settings.NotifierFCMProjectID,
    }))
}
```

`ResolveCredentialsFile` is a shared utility in `external/notifier` that
returns the credentials file path to use. If the base64 variant
(`NOTIFIER_FCM_CREDENTIALS_FILE_B64`) is set, it decodes the payload
into a temp file; otherwise it returns the file-path variant as-is.

This snippet records the original wiring decision. New integrations should use
`NewStandardSenders` and call its returned `Cleanup` function; callers that use
`ResolveCredentialsFile` directly own removal of any temporary file it creates.

If you prefer, you can provide `NOTIFIER_FCM_CREDENTIALS_FILE` and 
`NOTIFIER_FCM_PROJECT_ID` in the deployment environment. you will have to
make sure `NOTIFIER_FCM_CREDENTIALS_FILE` is accessible to be read.

```go
//...

notifierService.WithSender(notifier.NewFCMSender(notifier.FCMSenderConfig{
    Enabled:         settings.NotifierFCMEnabled,
    CredentialsFile: settings.NotifierFCMCredentialsFile,
    ProjectID:       settings.NotifierFCMProjectID,
}))
```


**Server-side changes required:**

- **Token invalidation**: Teach `FCMSender.Send()` to use the cleanup handler
  already installed by `Service.WithSender()` for senders that implement
  `InvalidAddressCleanable`. When FCM returns an error indicating a token is
  invalid (e.g. `Unregistered` error code), the sender should call
  `invalidAddressHandler` to disable the address via `DisableAddressByHash`.

  Unlike Web Push where the HTTP status indicates permanence, FCM errors come
  inside the Firebase Admin SDK response. The sender currently uses `go-fcm`
  directly (rather than `nikoksr/notify/service/fcm`) to ensure credentials are
  applied during `NewClient` construction. The sender sends single-token
  messages individually when one token is present. Multicast is used when there
  are multiple tokens. Per-token errors are included in the returned batch
  error, but they are not yet mapped back to stored address hashes for cleanup.

### 6. Config endpoint updates

When FCM is enabled, `GetConfig()` returns:

```json
{
  "supported_channels": ["FCM", "WEBPUSH"],
  "webpush": { "enabled": true, "vapid_public_key": "..." },
  "fcm": { "enabled": true }
}
```

The mobile client store should read this config before exposing registration
actions. Client-side provider availability and server-side channel availability
both need to be true before asking the user for notification permission.

### 7. Logout cleanup

The web client can perform best-effort Web Push deregistration during logout, but
that does not cover mobile/FCM tokens. The mobile notification store should
add an `unregisterDevice()` call that:

1. Lists the user's registered addresses via `GET /me/notifications/addresses`.
2. Deletes the current device's FCM address via `DELETE /me/notifications/addresses/{id}`.

The device identity can be matched using `device_id` (a UUID persisted in
secure storage, generated once on first launch). This ensures the FCM address
is cleaned up when the user signs out, preventing the next user from receiving
stale notifications.

### 8. Platform-level setup

The `firebase_messaging` Flutter package requires these platform changes
(outside the plan scope but noted for completeness):

- **Android**: Add `google-services.json` to `android/app/`, apply the
  `google-services` Gradle plugin in `android/build.gradle`.
- **iOS**: Add `GoogleService-Info.plist` to `ios/Runner/`, enable Push
  Notifications capability in Xcode, add `FirebaseMessaging` import to
  `AppDelegate.swift` or `AppDelegate.m`.
- **Web**: Not applicable for mobile push. The existing Web Push path
  (Push API + Service Worker) remains the web channel.

## Migration / data impact

| Concern | Impact |
|---------|--------|
| **Database schema** | None. The `notification_addresses` collection already stores FCM addresses. Existing Web Push records are unaffected. |
| **Existing indexes** | None needed. The unique index on `(channel, address_hash)` already covers FCM tokens. |
| **Existing preferences** | None. `DefaultNotificationPreferences` already enables FCM by default (`channels.FCM: true`). Existing users see mobile push enabled automatically when they register a device. |
| **Token deduplication** | Already handled by `hashAddress()` — same token from same device produces same hash, so re-registration after token refresh is an upsert. |
| **Stale tokens** | None as a schema-migration concern. Until automatic FCM invalid-address cleanup is completed, stale tokens remain active and may be retried; hosts should remove them through the address API or an application-specific cleanup flow. |

## Rollout risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| **Firebase credentials leaked** | Low | Critical | Store credentials in secrets manager (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault), never in env files or git. |
| **FCM quota exceeded** | Low | Medium | Monitor current usage and limits in Firebase Console and adjust the deployment plan when needed. |
| **Token invalidation not triggered** (notifyfcm batch error swallows per-token failures) | Medium | High | Refactor to send per-token (option a). Without this, stale tokens accumulate and every `NotifyUser` call wastes time trying invalid tokens. |
| **`firebase_messaging` Flutter package API changes** | Low | Medium | Pin to a known-good version in `pubspec.yaml`. The interface is mature and has been stable for several years. |
| **Users not prompted for notification permission** | Medium | Low | `requestPermission()` is called at registration time, not at startup. The system dialogue only appears when the user taps "Register". The store already guards with `isAvailable`. |
| **Token refresh race condition** | Low | Low | The `tokenChanges` stream emits on the main thread. Re-registration is async and the store sets `isRegisteringDeviceNotifications = true` to guard against double-registration. |
| **App store rejection (iOS)** — missing push entitlement or misuse of APNs | Low | Medium | Ensure the iOS Push Notifications capability is enabled in Xcode and the App ID has Push Notifications enabled in Apple Developer Portal. Firebase handles APNs certificate management. |
| **Production secret configuration drift** | Low | Medium | Add the Firebase credential reference to the host application deployment and verify it is injected as a mounted file or environment value. |
| **Backwards compatibility** — old clients sending requests without changes | None | — | The API is additive. Old clients continue to register Web Push addresses. The `fcm.enabled` field in the config response changes from `false` to `true` but the JSON shape is identical. |
